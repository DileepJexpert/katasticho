- [x] **C3. AR multi-invoice allocation + customer advance receipt** — **backend DONE + tested; Flutter DONE.** New `CustomerReceipt` + `CustomerReceiptAllocation` aggregate (V18 migration) — the AR mirror of `VendorPayment`/`VendorPaymentAllocation`, deliberately separate from the legacy single-invoice `Payment` so that path is byte-for-byte untouched (zero regression). `CustomerReceiptService.recordReceipt` collects one lump sum, allocates it across many open invoices (each ≤ its `balanceDue`, dedup-guarded, payable-status-gated), and parks the unallocated excess as a Customer Advance (CoA 2100) — `advance = amount − Σallocations`, `AR_RECEIPT_OVER_ALLOCATED` when negative. Journal via new `AccountingPostingEngine.postCustomerReceipt`: `DR Cash/Bank (by method) / CR AR (Σalloc at each invoice rate) / CR Customer Advance 2100 (excess) / Forex 5500 balancer` — collapses to the legacy 2-line shape for a single fully-applied INR allocation, balances for multi-currency. Each invoice settled via `invoiceService.updatePaymentStatus`; contact `outstandingAr` reduced by the **applied** amount only (advance is a liability, not an AR reduction). `voidReceipt` reverses the journal, restores every invoice balance + AR. Endpoints @ `/api/v1/customer-receipts` (record/list/get/void/`invoice/{id}`/`advance/{contactId}`).
